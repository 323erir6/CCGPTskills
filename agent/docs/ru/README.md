# GOCODE Agent — реализация и правила работы

Этот справочник описывает инженерный процесс на базе GitHub без дополнительных платных сервисов для проектов CC:Tweaked / NeoForge. Автономного платного сервера модели здесь нет. Английский справочник хранится отдельно: [English reference](../en/README.md).

## 1. Код → CI → диагностика → исправление → проверка

**Реализовано:** `.github/workflows/gocode-agent-ci.yml` выполняется после изменений и при создании pull request. Проверяет синтаксис Lua, запускает Python-тесты, выполняет повторяемые Lua-тесты и сохраняет отчёт JSON в артефактах GitHub Actions. Существующий workflow `lua-ci.yml` не изменяется.

**Цикл работы агента:** изучение результата CI и логов, формирование конкретной гипотезы, изменение кода в отдельной ветке, повтор тестов, независимая проверка diff. Повторять в рамках доступной сессии до прохождения тестов или документирования ограничений. При закрытом чате модель сама по себе не продолжает рассуждать. Для классификации логов: `python3 agent/scripts/diagnose.py path/to/log.txt`.

**Безопасные автоматические исправления:** `.github/workflows/gocode-autofix.yml` запускается вручную. Исправляет только оформление Python-файлов внутри `agent/`, создаёт отдельную ветку и открывает PR без автоматического слияния. Не исправляет алгоритмы случайными заменами. На GitHub может потребоваться разрешить Actions создание PR в `Settings → Actions → General` и выдачу нужных прав. Не следует предоставлять токены записи недоверенному коду чужих PR.

## 2. Машиночитаемый справочник API

`agent/api/*.json` хранит точные версии Minecraft и модов, исходный репозиторий и коммит, название периферии или глобального API, видимые методы, типы аргументов, возвращаемые значения и файл реализации. Записи разных версий не объединяются без проверки.

Уровни достоверности:

- `source-confirmed` — метод подтверждён Java-кодом и `@LuaFunction` либо регистрацией.
- `documentation-confirmed` — подтверждён документацией соответствующей версии.
- `runtime-confirmed` — непосредственно проверен на компьютере CraftOS в Minecraft.
- `unverified` — предположение, которое нельзя использовать как гарантированный API.

Команда `python3 agent/scripts/validate_api.py` проверяет структуру JSON, дубликаты и поля, но не доказывает эквивалентность реальной Java-реализации. Исходные снимки охватывают Programmable Fuzes 1.4.1, Enhanced Detector Radar 1.0.5, Sable CC Tick Sync 1.6.4 и Mianbao Sable Explosion Compat 1.2.9.

## 3. Локальная симуляция периферии — принцип реализации

Макеты **не являются Minecraft** и не воспроизводят весь CraftOS или физический движок Sable. Они предоставляют детерминированные замены отдельных функций, позволяющие тестировать неизменённые алгоритмы Lua.

| Модуль | Что имитируется | Что не имитируется |
| --- | --- | --- |
| `agent/mocks/peripheral.lua` | Подключение, отключение, типы, методы, wrap/find/call | Java-планировщик и capabilities |
| `agent/mocks/clock.lua` | Виртуальное время, таймеры, очередь событий | Реальное ожидание, весь parallel |
| `agent/mocks/rednet.lua` | Несколько компьютеров, фильтры пакетов, потеря пакета | Радиосеть, задержки, шифрование |
| `agent/mocks/redstone.lua` | Логический/аналоговый сигнал, пределы и история | Поведение блоков мира |
| `agent/mocks/sublevel.lua` | Искусственные данные координат и скорости | Физика, столкновения и ограничения |

Пример:

```lua
local Mock = require('agent.mocks.sublevel')
local transform = require('lib.sublevel_pose')
local ship = Mock.new()
ship:setVelocity({x=0,y=0,z=20})
local state = ship:api()
local p = transform.localToWorld({x=2,y=3,z=4}, state.getLogicalPose())
assert(p.x == 2 and p.y == 3 and p.z == 4)
```

Модели движения, задержки и имитация сбоев могут быть добавлены после определения ожидаемого поведения. Координатные соглашения, частота физических шагов и внешние методы всё равно нуждаются в проверке по реальным версиям модов. Запуск из корня репозитория: `lua5.3 agent/tests/test_mocks.lua`, `lua5.3 agent/tests/test_integration.lua`. CraftOS-PC может дополнять тестирование, но не содержит автоматически все периферии модов.

## 4. Анализ JAR и исходников на стороне ассистента

Подключённый GitHub и временная среда анализа позволяют изучать Java-код и доступные JAR **без установки инструментов на компьютер пользователя**. Нужно искать `@LuaFunction`, `ILuaAPI`, `IPeripheral`, `GenericPeripheral`, регистрацию возможностей, возвращаемые таблицы и события. Проверять совпадение версии исходного кода и установленного JAR. Если бинарный архив недоступен, честно указывать ограничение. Не загружать чужой закрытый исходный код и большие бинарники в эту библиотеку. Автоматическая выгрузка архивов из GitHub Actions не настроена.

## 5. Независимая проверка кода

После реализации отдельно анализировать фактический diff: логика, граничные условия, API, потокобезопасность, недоверенный ввод, права, утечки ресурсов, совместимость, производительность и лишние изменения. `agent/scripts/review.py` — только простой поиск типичных Lua-ошибок. Он не заменяет CodeQL или полноценный аудит. Для Java-модов следует включать проверки в их исходных репозиториях.

## 6. Постоянный контекст

В `agent/context/*.template.*` хранятся шаблоны архитектуры, API, состояния разработки и известных дефектов. Копии следует сохранять в соответствующих проектах и заполнять подтверждёнными фактами с привязкой к исходникам, тестам и коммитам. Файлы переживают смену чатов благодаря GitHub. Старые записи не приоритетнее текущего исходного кода.

## 7. Ветки и Pull Requests

Значимые изменения выполняются в тематической ветке; `.github/pull_request_template.md` содержит контрольный список проверки. Результаты CI видны рядом с PR. Защиту главной ветки администратор должен включить отдельно, если она требуется. Никакого принудительного push или автоматического слияния без разрешения.

## 8. Измеряемые регрессионные тесты

`agent/benchmarks/cases.json` содержит детерминированные случаи. `agent/scripts/benchmark.py --output agent-results/benchmark.json` запускает их и записывает успешность, время и вывод. Отчёт загружается в артефакты CI. Пройденные проверки доказывают только соответствие конкретным тестам, **не** общий уровень интеллекта модели. Для каждого значимого исправления полезно добавлять воспроизводящий тест.

## 9. Автоматический выбор режима работы

В `agent/AGENTS.md` определены режимы `research`, `architect`, `implement`, `debug`, `test`, `review`, `refactor` и `release`. Ассистент выбирает основной режим и переключается по ходу задачи. Явный выбор пользователя приоритетнее. Активация GOCODE как общего процесса — отдельная настройка. Постоянный фоновый наблюдатель не устанавливается.

## 10. Сборка артефактов

`agent/templates/java-neoforge-ci.yml` — шаблон GitHub Actions для Java 21 / NeoForge / Gradle, выполняющий сборку и сохраняющий `.jar`. `agent/templates/python-ci.yml` — шаблон тестов Python. Шаблоны не внедряются автоматически в чужие репозитории: их необходимо скопировать и адаптировать. Развёртывание, публикация релиза и слияние PR требуют разрешения.

## Границы бесплатности

Обычные GitHub-hosted runners преимущественно бесплатны для открытых репозиториев, с ограничениями сервиса. Для приватных репозиториев действуют включённые лимиты, дополнительные ресурсы могут тарифицироваться. Основные инструменты используют Python stdlib и Lua 5.3. Время работы GitHub Actions **не включает** бесплатные вызовы моделей ChatGPT API.
