# Sable CC Tick Sync 1.6.4

**Источник:** [Sable-CC-Tick-Sync](https://github.com/323erir6/Sable-CC-Tick-Sync), коммит `32ed09ce8e8944ee20b3787b547971617003fafb`. Методы подтверждены в `SableSyncApi.java`, планировщик изучен по `HighFrequencyController.java` и сопутствующим классам.

## Точный Lua API

Глобальная таблица `sableSync` имеет два метода только для чтения:

| Метод | Аргументы | Возвращает |
| --- | --- | --- |
| `sableSync.isHighFrequency()` | нет | boolean: ускорен ли компьютер |
| `sableSync.getPhysicsFrequency()` | нет | number: частота физических подшагов, Гц; 0 до первого корректного шага |

Устаревший `sableSync.setHighFrequency()` **удалён**. Вручную включать частоту не нужно: мод автоматически ускоряет компьютеры при наличии соответствующей физической среды.

```lua
assert(type(sableSync)=="table","Tick Sync API not installed")
print(sableSync.isHighFrequency(),sableSync.getPhysicsFrequency())
```

## Поведение планировщика

- Lua-потоки и исполнитель получают возможность работы на физических подшагах Sable.
- Таймеры CC, опрос Redstone и другие состояния, зависящие от игровых тиков, остаются привязаны к 20 TPS.
- Обычная обработка тика Minecraft сохраняется для событий, подключения устройств и надёжной обработки внешнего ввода. Соответствующий физический шаг не дублируется.
- Часть вызовов периферии основного потока допускается в ограниченную очередь физического шага.
- Встроенные CC-периферии и GPU/мониторы Tom's используют обычную очередь 20 TPS там, где это необходимо.
- Опасные синхронные вызовы Rapier из рабочего Lua-потока перенаправляются на серверную очередь.

## Точные ограничения исходного кода

`HighFrequencyController.java` устанавливает `MAX_PENDING_FAST_TASKS=4096` ожидающих операций, `MAX_TASKS_PER_SUBSTEP=1024` обслуживаемых операций на подшаг и общий бюджет `MAX_TASK_TIME_PER_SUBSTEP_NANOS=2_000_000` (**2 мс**). Это верхние границы, не гарантия скорости. Переполнение может привести к отказу постановки очередной операции.

## Разработка регуляторов

`sleep(0)` не гарантирует одну итерацию на каждый физический подшаг. `sleep(0.001)` также нельзя считать гарантией частоты 1000 Гц. Измеряйте фактический `dt`, проверяйте `getPhysicsFrequency()`, сохраняйте корректные единицы импульса/силы и учитывайте задержку обработки периферии.

## Проверка

После запуска физики вызывайте `sableSync.getPhysicsFrequency()`. Для тестирования Java-планировщика репозиторий предлагает `gradlew regressionTest`; он не заменяет нагрузочных испытаний внутри игры.

**Совместимость по README:** Minecraft 1.21.1, Sable 2.0.5, CC:Tweaked 1.120.0.

Отдельных новых периферийных методов мод не регистрирует; кроме `sableSync`, он изменяет внутреннее расписание работы компьютеров.
